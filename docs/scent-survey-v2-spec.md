## 1. 현행 진단 — 무엇이 왜 문제인가

### 1-1. 배점 방향과 화면이 모순된다 (최우선)

현재 배점은 `a=4 ... d=1`(좋은 상태일수록 고점)인데, 추천은 **최저점 축**으로 이루어진다.
결과 화면의 바 차트는 고점 축을 길게 그리므로, 사용자는 "제일 긴 몰입(92점)이 내 결과여야 하는 것 아닌가"로 읽는다.
실제 사례: 숙면 33점(최저) → 결과 "숙면케어". 화면상 근거가 보이지 않는다.

또한 같은 화면의 레이더 차트는 "중심에 가까울수록 케어 필요"라는 반대 방향 규칙을 쓴다.
**한 화면에 방향이 상반된 시각화 두 개가 공존한다.**

### 1-2. 동점이 예외가 아니라 기본값이다

축당 4문항 × 4점 = 4~16점. 가능한 값이 13개뿐이라 5개 축 중 동점이 매우 흔하다.
실제 사례에서도 숙면 33 = 활력 33 동점이었고, 왜 숙면이 선택됐는지 화면에 설명이 없다.
동점 처리 규칙 자체가 정의되어 있지 않다.

### 1-3. 축 간 점수를 직접 비교할 수 없다

축마다 문항 난이도가 다르다. 예를 들어 화면 사용시간·환기 횟수 문항은 대부분의 응답자가 같은 구간에 몰려,
해당 축은 구조적으로 낮은(또는 높은) 점수가 나온다. 원점수를 그대로 비교하면 **특정 향으로 결과가 쏠린다.**

### 1-4. 향 취향을 묻지 않는다

상태 진단만으로 향을 정하므로, 라벤더를 싫어하는 사람에게도 라벤더가 BEST로 노출된다.
향 만족도의 최대 예측 변수가 설문에서 빠져 있다.

### 1-5. 기준 기간이 섞여 있다

일부 문항은 "어제", 일부는 "최근 일주일", 일부는 기간 없음. 응답 요일에 따라 결과가 흔들려 재검사 신뢰도가 낮다.

### 1-6. 규제·표현 리스크

- 심장 두근거림 등 증상 문항은 개인정보보호법상 **민감정보(건강정보)** 로, 별도 동의가 필요하다.
- "GABA-A 수용체를 조절해 신경 흥분을 낮추고 서파수면을 늘림" 같은 기전 서술은 **효능 표방**으로 읽힐 소지가 있다.

### 1-7. 개인화 학습의 입력이 없다

추천한 향을 실제로 사용했는지, 만족했는지를 수집하지 않는다.
**이 루프가 닫히지 않으면 데이터가 아무리 쌓여도 개인화가 불가능하다.**

## 3. 스코어링 로직

추천 엔진은 **순수 함수로 분리**한다. 화면·DB와 섞지 말 것.

```
input:  { itemScores, axisScores, surveyCount, baseline, cohortStats,
          preferences, avoid, space, safety }
output: { primaryAxis, tieBreakReason, scents[], filteredOut[], appliedFilters[] }
```

### 3-1. 축 점수

각 축 3문항 합산 → **3~12점**. 높을수록 케어가 필요.

| 축 | 문항 | 추천 향 |
|---|---|---|
| 숙면 | Q1, Q6, Q11 | 숙면 향 |
| 이완 | Q2, Q8, Q14 | 이완 향 |
| 활력 | Q5, Q9, Q13 | 활력 향 |
| 몰입 | Q4, Q10, Q15 | 몰입 향 |
| 청정 | Q3, Q7, Q12 | 청정 향 |

### 3-2. 축 간 표준화

**원점수를 그대로 비교하지 않는다.** 축마다 평균이 다르기 때문이다.

```
z_between = (개인 축 점수 − 해당 축의 전체 평균) / 해당 축의 표준편차
```

- 코호트 통계(평균·표준편차)는 별도 테이블에 저장하고 배치로 갱신한다.
- **응답 200건 미만이면** 코호트 통계가 불안정하므로 원점수 비교로 폴백한다.
  단, 이 상태임을 어드민에서 확인할 수 있어야 한다.
- 200건 도달 시 축별 분포를 반드시 점검한다. **특정 향이 40%를 넘으면 그 축의 문항 보기 구간을 조정한다.**

### 3-3. 개인 기준선 (2회차 이상)

```
baseline[axis]   = 1~2회차 축 점수의 평균
sd_within[axis]  = 개인 관측치의 표준편차 (관측 3개 이상일 때만)
z_within         = (이번 점수 − baseline) / sd_within
```

- **관측 3개 미만이면 z_within을 계산하지 말고 null로 둔다.**
- 2회차 이상에서는 추천 기준을 `z_between` → `z_within` 으로 전환한다.
  집단 대비보다 본인 대비 변화가 개인화에 더 유효하다.

### 3-4. 동점 처리

Q18(사용 공간)으로 자동 해결하고, **그 이유를 결과 화면에 노출한다.**

| Q18 응답 | 우선 축 |
|---|---|
| 침실 | 숙면 > 이완 |
| 거실·주방 | 이완 > 청정 |
| 사무실·작업공간 | 몰입 > 활력 |
| 차량 | 활력 > 몰입 |
| 기타 | 아래 기본 순서 |

여전히 동점이면 기본 순서: **숙면 > 이완 > 활력 > 몰입 > 청정**

`tieBreakReason` 을 반환값에 담아 화면에서 문장으로 표시한다.

### 3-5. 전 축 양호

모든 축의 z가 0 미만(또는 코호트 통계 부재 시 모든 원점수 ≤ 5)이면
특정 향을 억지로 추천하지 말고 **"시그니처 / 데일리" 분기**로 보낸다. SKU는 Q16 선호 계열로 고른다.

### 3-6. 필터 (추천 확정 직전에만 적용)

**순서가 중요하다. 상태로 "어떤 향"을 정하고, 취향으로 "어떤 제품"을 정한다. 순서를 바꾸면 진단이 무의미해진다.**

1. Q17 비선호 계열에 해당하는 SKU 제외 → 같은 축의 대체 SKU로 교체
2. Q16 선호 계열과 겹치는 SKU 우선 정렬
3. Q19 안전 플래그 → 저농도·안전 라인으로 분기 + 안내 문구 노출
   - 임신·수유 중 → 해당 SKU 제외 및 사전 상담 안내
   - 알레르기 경험 → 패치 테스트 안내
   - 어린이·반려동물 → 확산 방식 권고 변경
4. 필터로 모든 SKU가 제외되는 경우의 폴백을 반드시 정의한다 (안전 라인 기본 SKU)

`filteredOut[]` 과 `appliedFilters[]` 를 반환해 화면에서 근거를 보여준다.

### 3-7. 응답 품질 플래그

- **straight-lining**: 정방향 문항과 역방향 문항(Q3·Q8·Q9·Q11·Q15)의 응답이 체계적으로 모순되면 플래그
- **응답 시간 이상**: 총 응답시간이 비정상적으로 짧으면 플래그
- 플래그된 응답은 코호트 통계 계산에서 제외한다 (사용자에게는 정상 노출)

### 반드시 지킬 것

- **`item_scores` 를 문항 단위로 저장한다.** `axis_raw` 만 저장하면 나중에 축을 재정의하거나
  문항 신뢰도를 분석할 때 과거 데이터를 재계산할 수 없다.
- **`daily_checkins` 를 `responses` 와 섞지 않는다.** 섞으면 시계열이 오염된다.
- `survey_version` 이 바뀌면 그래프를 **끊어서** 그린다. 다른 문항으로 잰 값은 같은 선 위에 올릴 수 없다.

### 기존 데이터 마이그레이션

기존 응답이 있다면 배점 반전 전에 처리한다.

1. 기존 응답 전체에 `survey_version = 'v1'` 부여
2. v1 데이터는 **점수 변환하지 말고 그대로 보존** (v1 정의를 `survey_versions` 에 함께 저장)
3. v1과 v2를 같은 시계열·같은 코호트 통계에 섞지 않는다
4. 사용자에게는 "설문이 개선되어 이전 결과와 점수 기준이 다릅니다" 안내

## 5. Phase 1 — 로직 · 스키마 (화면 손대기 전)

> 화면을 먼저 고치면 로직 변경 시 전부 다시 고쳐야 한다. 반드시 이 순서로.

1. **문항 정의를 코드에서 분리**한다.
   `survey_definitions/v2.json` 형태로, 각 문항은
   `{ id, axis, reverse, text, options: [{ label, score }] }` 구조.
   하드코딩된 문항이 있다면 전부 이 정의를 참조하도록 교체.

2. **배점을 반전**한다 (`a=1 ... d=4`). 위 §2 보기·배점표를 그대로 적용.

3. **DB 스키마를 §4대로 추가/변경**하고 마이그레이션을 작성한다.
   기존 데이터가 있으면 v1 태깅 마이그레이션을 먼저 실행.

4. **추천 엔진을 순수 함수로 분리**한다 (`lib/recommend.ts` 등).
   §3의 로직 전체를 여기에 구현. DB·화면 의존성 없이 입력→출력만.

5. **테스트를 반드시 붙인다.** 최소 아래 케이스:
   - 단일 최고점 (정상 경로)
   - 2개 축 동점 → 공간별 tie-break 각각
   - 3개 이상 축 동점
   - 전 축 양호 → 시그니처 분기
   - 비선호 필터로 1순위 SKU 제외
   - 필터로 모든 SKU 제외 → 폴백
   - 안전 플래그(임신) 조합
   - 코호트 통계 부재 시 원점수 폴백
   - 관측 2개일 때 z_within 미계산

6. **응답 품질 플래그** 계산 로직 추가 (§3-7).

7. **Part B(Q16~Q20) 문항 정의와 응답 수집을 Phase 1에 포함한다.**
   Q16·Q17·Q19는 필터의 입력, Q18은 동점 처리의 입력이다. 즉 **추천 엔진의 필수 입력값**이므로

   - Phase 1: 문항 정의(v2.json), 응답 저장 스키마, 최소 동작 UI, 동의 체크박스

8. **테스트 프레임워크가 없으면 먼저 도입한다** (vitest 권장).

## 6. Phase 2 — 결과 화면

7. **점수 시각화 수정**
   - 바 차트 라벨: `"점"` → `"케어 필요도"`
   - 정렬: 높은 순 (추천 축이 맨 위)
   - 색상: 1위만 브랜드 강조색, 나머지는 중립 회색.
     현재는 축마다 다른 색인데 색이 상태를 인코딩하지 않아 의미가 없다.
   - **레이더 차트: 세부 팩셋 구조를 유지한다.** (v2.1 수정 — 아래 참고)
     - 팩셋(입면/깊은 수면/개운한 아침/수면 리듬)은 **팩셋별 향 매칭의 근거**이므로 없애면 안 된다
     - **방향만 바 차트와 통일**한다: "바깥 = 케어 필요"
     - 차트 제목에 축을 명시한다: `"숙면 영역 상세"` — 바 차트(5축)와 축 정의가 다르다는 것이 보여야 한다
     - 방향을 통일하면 **가장 뾰족한 팩셋 = BEST 향**이 되어 직관적으로 읽힌다
   - 한 화면에 방향이 반대인 시각화가 공존하면 안 된다. 이것이 원래 문제였고,
     레이더를 없애는 것이 아니라 **방향을 맞추는 것**이 해법이다.

> **v2.1 수정 이력** — 초판 §6-7은 "레이더를 5축으로 교체"였으나, 코드 확인 결과
> `computeFacetScores()` / `matchScentPerFacet()` 이 팩셋 단위로 향을 매칭하고 있어
> 교체 시 향 추천 로직 자체가 소실된다. 팩셋 구조를 유지하고 방향만 통일하는 것으로 정정한다.

### A-2. 팩셋 시스템은 유지한다 (중요)

`matchScentPerFacet()` 은 축 내부 팩셋별로 향을 매칭한다. 결과 화면에 향이 4종 나오는 근거가 이것이다.
**이 로직을 제거하거나 5축 레이더로 대체하지 말 것.** §6-7 v2.1 수정을 따른다.

배점 반전 시 `computeFacetScores()` 의 0~100 정규화 방향도 함께 뒤집어야 한다.
그리고 **화면 표시용 0~100 값과 저장용 원점수를 분리한다.** DB에는 원점수(`item_scores`, `axis_raw`)를 저장하고,
0~100은 렌더링 시점의 변환으로만 쓴다. 정규화된 값만 저장하면 나중에 재계산이 불가능하다.

### A-3. Supabase 마이그레이션 체계 도입

현재 스키마가 대시보드 직접 실행으로 만들어져 버전 관리 밖에 있다. Phase 1에서 정리한다.

```
1. supabase/migrations/ 디렉터리 생성
2. 현재 scent_results 스키마를 baseline 마이그레이션으로 덤프
   (supabase db pull 또는 대시보드에서 DDL 추출)
3. 이후 모든 스키마 변경은 마이그레이션 파일로만 진행
4. §4 스키마를 새 마이그레이션으로 작성
```

**대시보드에서 직접 DDL을 실행하지 말 것.** 로컬과 프로덕션 스키마가 갈라지면 원인 추적이 불가능해진다.

### A-4. 사용자 식별 체계 (확정 — 2026-08-27)

**`users` 테이블을 별도로 만들지 않는다.** 이미 27명이 들어 있는 `kakao_users` 테이블을 그대로 쓰고,
`uuid` 컬럼(`id`)만 추가한다. 로그인 플로우(PK `kakao_id`)는 건드리지 않는다.

```sql
alter table public.kakao_users
  add column if not exists id uuid not null default gen_random_uuid();

create unique index if not exists kakao_users_id_key
  on public.kakao_users(id);
```

- 모든 신규 테이블(`responses`, `user_baselines`, `daily_checkins`, `merged_anon_ids`)의
  `user_id` 는 `kakao_users.id` 를 참조한다.
- `scent_results.kakao_id` → `kakao_users.kakao_id` 매핑 관계는 유지.
- 002 마이그레이션에서 `users` 테이블 생성 블록 제거 완료.
- 003 마이그레이션의 `merged_anon_ids.user_id` 참조를 `kakao_users(id)` 로 수정 완료.

**비로그인 사용자**: 익명 세션 ID(`anon_id`)로 저장 → 로그인 시 `merge_anon_responses()` 함수로 1회 병합.

### A-5. 테스트 프레임워크

`package.json` 에 테스트 러너가 없으면 **vitest를 먼저 도입한다.**
`recommend.ts` 는 순수 함수이므로 DOM 없이 테스트 가능하다. §5-5의 9개 케이스가 최소 요구다.

### A-6. ScentResultPage.tsx 분해

1,035줄 단일 파일이라 Phase 2에서 손대기 어렵다. **다만 전면 리팩터링은 하지 말 것.**
Phase 2에서 실제로 수정하는 부분만 컴포넌트로 분리한다.

```
ScoreBarChart / FacetRadarChart / ScentCard / ScentFeedback / ResultCTA
```

건드리지 않는 영역은 그대로 둔다. 범위를 넓히면 회귀 위험만 커진다.

### A-7. 로컬 실행 시 Supabase 비활성

`isProductionEnv` 체크로 프로덕션에서만 Supabase에 연결된다.
Phase 1의 저장 로직을 로컬에서 검증하려면 **로컬 개발용 Supabase 프로젝트 또는 `supabase start`(로컬 스택)** 가 필요하다.
프로덕션 DB에 직접 테스트 데이터를 쓰지 말 것 — 코호트 통계가 오염된다.
